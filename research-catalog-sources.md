# Legal/compliant grocery catalog data sourcing (US, mid-2026)

**Bottom line:** Kroger's public Products + Locations API is the only genuinely official, free, self-serve, store-specific catalog/availability rail among the six chains. Nothing comparable exists for Target, Costco, Trader Joe's, or Whole Foods — treat "what does this chain carry" as unknown for those four absent a BD deal. For chain-agnostic product identity (name/brand/size), stack Open Food Facts (free, thin US coverage) + USDA FoodData Central (free, clean, monthly updates) as the default, paying for Edamam/Spoonacular/UPCitemdb only if broader UPC coverage is worth the ToS friction. Scraping retailer sites for "general what a chain carries" is a ToS/contract-law no-go regardless of the CFAA question — hiQ v. LinkedIn narrows criminal/CFAA exposure, not breach-of-contract exposure.

## 1. Official retailer/partner APIs

**Kroger — the only real official rail.** Public Products API uses OAuth2 `client_credentials` grant with the `product.compact` scope, no end-user login required; signup is self-serve via a free developer.kroger.com account. Store-specific pricing/availability requires a `locationId` param pulled from the separate Locations API. Rate limits: Products capped at 10,000 calls/day (shared across product ops), Locations capped at 1,600 calls/day per endpoint. No published cost for the public tier. A separate, higher-privilege "Partner" tier exists behind a signed, non-public agreement with unpublished pricing/terms — confirm the Public tier's Acceptable Use language on storage/redistribution before architecting persistence around it, since the terms page itself resisted direct fetch (JS-rendered SPA) in this research pass and was only corroborated via third-party sources quoting it. *(developer.kroger.com/api-products/api/product-api-public; developer.kroger.com/reference/api/product-api-partner; corroborated via kroger-api PyPI/GitHub and Postman's official Kroger workspace docs; checked July 2026.)*

**Walmart — no general catalog API.** Two narrow, purpose-gated programs, neither answers "does Walmart carry X" for a shopping feature: (a) Content Provider/Affiliate API — read-only, approval-gated, meant for building tracked affiliate links, not general catalog use; (b) Marketplace/Item Management API — sellers-only, scoped to items that seller actively lists, not the general catalog. Access model is being restructured this year: Solution Provider "Delegated Access" key creation retires July 30, 2026, existing keys stop working October 1, 2026, forcing migration to OAuth2. *(developer.walmart.com/us-marketplace; developer.walmart.com/doc/us/mp/us-mp-items/; marketplacelearn.walmart.com; checked July 2026.)*

**Target RedSky — unofficial, not a compliant option.** RedSky is Target's internal frontend API, reverse-engineered by outside developers; no published ToS grant or license exists. The one claim of informal Target "endorsement" traces to a low-provenance, undated GitHub gist comment — not legal cover. This was directly contradicted by a primary source found in verification: Target's own engineering blog (tech.target.com/blog/empowering-clients-api) describes RedSky as an internal-only platform serving roughly thirty internal client teams, with no mention of external developer access. External RedSky users report increasing IP blocking. **Verdict: keep off a compliant product, and the evidence for "unofficial" got stronger on verification, not weaker.**

**Costco / Trader Joe's / Whole Foods — no official feed at all.** Exhaustive search (mid-2026) surfaced only third-party scraping-as-a-service vendors marketing themselves as "APIs" (e.g. a "Whole Foods Grocery Data Scraping API" product) and a defunct 2011 community project. There is no licensed retailer feed for any of the three. Packaging scraping as a paid "API" doesn't remove the underlying ToS-breach exposure against the retailer — it outsources it, and adds a second point of failure (the vendor itself getting cut off or sued).

## 2. Open datasets

**Open Food Facts (OFF):** free, crowdsourced (photos/barcode scans/OCR), ODbL 1.0 for structure + Database Contents License for data (images CC-BY-SA). Commercial use is explicitly allowed but requires attribution **and share-alike** — a proprietary catalog that merges/enriches OFF data can trigger an obligation to publish that derivative back under ODbL. No formal freshness SLA; a third-party analysis found ~80% of products missing packaging info, ~64% missing Eco-Score. US chain coverage is real but thin: roughly 3,300-3,600 tagged products per major chain (Kroger 3,504; Trader Joe's 3,392; Meijer 3,639) against an average US supermarket carrying ~33,248 distinct SKUs (FMI, 2025) — OFF covers roughly 10% or less of a single store's actual assortment, skewed toward shelf-stable packaged goods (produce/deli/bakery/meat are near-absent, no UPCs). The API itself is designed for "1 API call = 1 real user scan," not bulk catalog building — full daily exports are the sanctioned path for bulk use, and scraping the API is explicitly likely to get blocked. *(us.openfoodfacts.org; world.openfoodfacts.org/terms-of-use; world.openfoodfacts.org/data; checked July 2026.)*

**USDA FoodData Central (FDC) Branded Foods:** ~2,013,644 records as of mid-2026, public domain / CC0-equivalent ("no permission needed," attribution requested not required) — cleanest license of anything in this space. Live API/online tool updates monthly (v15.3 on 2026-07-23, v15.2 on 2026-06-25, etc.); the full bulk-download file (GBFPD) updates only twice a year (historically ~April/October). It's a nutrition/ingredient identity database with UPC/brand-owner fields, **not** a per-retailer or per-store shelf-availability database — using it to answer "does this store carry it" produces false positives (item exists in the DB, isn't necessarily sold by that chain/store).

**Verdict:** OFF + FDC together are a fine, free default for general product identity (name/brand/size/UPC), and FDC's license is strictly better than OFF's for a proprietary product (no share-alike). Neither substitutes for per-chain/per-store availability truth.

## 3. Third-party commercial catalog APIs

Spoonacular ($0 free tier up to ~$149+/mo) covers ~86k food items; Edamam ($0 up to $999+/mo) covers ~900k items plus 700k+ UPC/EAN codes. Both target consumer nutrition/recipe apps. Edamam's own docs explicitly prohibit scraping/bulk-collecting its data and restrict storing/caching responses beyond presenting them to the requesting end user, unless a specific paid plan grants caching rights — pulling Edamam data straight into a persistent pantry DB on the wrong plan is itself a ToS violation, independent of any scraping question. Spoonacular's equivalent storage clause was not independently verified in the underlying research. UPCitemdb offers a free tier (100 lookups/day) scaling to 200,000+/day against a 717M-barcode database updated daily, but it's a barcode-to-name lookup, not a retailer catalog/availability API, and its commercial-use ToS specifics were not directly confirmed. **Evidence gap:** the requested deep-dive on pricing tiers/ToS suitability (report axis 3) and the full scraping-legality report (axis 4) were not delivered in full to this synthesis step — the above is reconstructed from what surfaced incidentally in the official-APIs report; treat storage/caching terms for all three vendors as needing a direct ToS read before committing engineering time.

## 4. Scraping retailer sites directly

hiQ v. LinkedIn (9th Cir., reaffirmed April 18, 2022; case fully resolved via private settlement Dec 2022, not further appealed) held that scraping data a site shows to logged-out/public visitors likely doesn't violate the CFAA's "without authorization" prong. Four independent law-firm analyses (Jenner & Block, Loeb & Loeb, Fenwick, Skadden) converge on the same reading with one critical caveat: **this only narrows CFAA (an anti-hacking statute) exposure — it does nothing for breach-of-contract exposure from violating a site's Terms of Service**, and does nothing to stop technical countermeasures (IP blocking, cease-and-desist). A retailer's ToS almost universally prohibits automated/bot access regardless of whether the data scraped is "public." Building a consumer product's catalog layer on scraped retailer data (directly, or via a third-party "scraping API" vendor) is one cease-and-desist away from losing that data layer entirely — a business-continuity risk, not just a legal footnote. **Verdict: "general what each chain carries" scraping is a no-go for a compliant product**, independent of the CFAA question, for all of Target/Costco/TJ's/Whole Foods.

## Where the evidence was weak

- Kroger's Acceptable Use terms on storage/redistribution rights were never directly fetched (SPA blocked WebFetch) — corroborated only via third parties quoting the docs. High confidence on scope/auth/rate-limits, unconfirmed on commercial persistence rights. **Verify before architecting.**
- The claim that "Target reps said RedSky is intentionally public" is a single undated, low-provenance GitHub gist comment — verification found a primary Target source (tech.target.com engineering blog) contradicting it, calling RedSky internal-only. This claim should be treated as false, not just unverified.
- Walmart's 2026 Delegated Access retirement dates (July 30 / Oct 1) rest on developer.walmart.com + one secondary summary — corroborated on verification, medium-high confidence.
- Third-party commercial API pricing/ToS (axis 3) and the full scraping-legality axis (axis 4) reports were not delivered complete to this synthesis; the third-party API section above is reconstructed from incidental findings in the official-APIs report and should be treated as a partial answer, not exhaustive.
- Spoonacular's data-storage/caching ToS clause and UPCitemdb's commercial-use ToS were flagged as "not independently verified" in the source research — don't build persistence on either without a direct ToS read.
