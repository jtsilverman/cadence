# Spec: consumption-expiry (pantry ages honestly, the diary becomes readable, one golden household guards it all)

Jake's build-the-backend loop directive (2026-07-26): "pantry to shopping list to consumption/expiration built in with meal history and schedule", history readers for every lane, "eval sets built to test changes". Third data-layer spec of the day; stacked on workout-engine.

**Intent.** Three additions, all deterministic readers/additive fields. (1) **Expiry, user-stated only**: a pantry assertion can carry `expires: "YYYY-MM-DD"` (no invented shelf-life tables — stating expiry is asserting pantry truth, exactly the suggest-only rule's territory for humans); the pantry fold carries it, GET /api/pantry surfaces items expiring within 7 days, and the list-build response connects them to action: "use soon" suggestions naming cookbook recipes that use the expiring item — data only, nothing scheduled for you. (2) **Consumption**: a pure reader turns RecipeCooked history into per-item weekly usage rates, surfaced on the pantry (the P3 "consumption view" made real, cold-start honest). (3) **History**: the diary becomes readable per lane — meals cooked, workout sessions, journal entries, sleep nights — one GET /api/history with device revisions resolved latest-per-external_id, never double-shown. Plus the **golden household**: one synthetic three-week diary fixture exercising every event type in the system, with assertions across every reader (pantry, fullness, cadence/replenish, schedule+recovery, exercise history, progression, goals, proposer, histories, consumption, expiry) — the regression eval future changes run against.

**Acceptance criteria.**
1. **Expiry contract.** `PantryAssertedPayload` gains additive `expires?: string` (calendar-valid, `isValidDate`); `parseAssertion` accepts it (422 reason on invalid); asserting with `expires` stores it, asserting the same item without `expires` clears it (an assertion is absolute truth — partial-keep would be a merge, not an assertion); inflows and cooks preserve the standing expiry (quantity changes don't move a date); cook-to-zero deletes the item, expiry included. `expires: null` and absent both clear (assertion is absolute; unlike qty/unit there is no explicit-null-required precedent to keep — reviewer finding 3); invalid strings 422. The fold's degrade branches (inflow/cook unit mismatch → present-unknown) preserve expiry, tested as their own case (finding 5); cook-to-zero deletes the item and a later inflow re-creates it WITHOUT expiry (inflows never state dates — named, intended). `pantry_view` gains an `expires` column via the schema's first additive column: migrate() checks `PRAGMA table_info` and ALTERs only when missing, catching the race where a parallel cold-start request ALTERed between check and execute (re-check after catch; genuinely-failed ALTER still throws — finding 2). Wipe-and-rebuild invariant extended with expiry events.
2. **Expiring surface.** GET /api/pantry returns per-item `expires` plus `expiring: [{name, expires}]` — items with `expires` ≤ today+7 (household-local today), soonest first, already-expired included and flagged (`expired: true`).
3. **Use-soon connects to meals.** `useSoonSuggestions(expiring, recipes-with-plans)`: for each expiring item, cookbook recipes whose ingredient names include it (normalized name match, the pantry-diff convention) → `[{name, expires, recipes: [{library_id, title}]}]`. Served in the /api/cart build response as `use_soon` (in-context, the Replenisher placement rule) and on GET /api/pantry. No events written, nothing auto-added to list or schedule.
4. **Consumption rates.** `lib/consumption.ts weeklyUse(events)`: per pantry-normalized ingredient name, total cooked quantity per week where units convert (sum via `convert` into the first-seen unit; incompatible cooks excluded from the rate, counted separately as `cooks_per_week`), observed window = first-to-last cook ts (minimum 1 week, household-local); <2 compatible cooks → no rate for that item (cold-start honesty). Events sorted byFoldOrder before folding so "first-seen unit" is caller-order-independent (the rebuildPantry rule; finding 4 — order-independence tested). GET /api/pantry items gain `weekly_use?: {qty, unit}` where a rate exists.
5. **History readers.** `lib/history.ts`: `mealHistory` (RecipeCooked → {date, title, library_id}, newest first), `workoutHistory` (SessionLogged latest-per-external_id → {date, title, kind, source, session_id?, library_id?}), `journalHistory` (JournalEntry → {date, text, slot_id?}), `sleepHistory` (SleptLogged latest-per-external_id → {date, quality, hours?, score?, source} — one row per night, latest event per date wins, the recovery-view rule). All dates household-local via `localDate`. GET /api/history?kind=meals|workouts|journal|sleep&limit=N (default 50, newest first; bad kind → 422).
6. **Golden household.** `tests/golden-household.test.ts`: one hand-written ~3-week diary fixture containing every event type (asserts incl. expiry, inflows, orders incl. instore run, cooks, prefs, schedule snapshots, session/set/sleep/journal/skip logs, whoop-sourced recovery+sleep+workout incl. one revision pair, goals incl. one cleared, suggestions pair). Assertions on every reader: pantry fold (incl. expiry + rebuild), cooksLeft, medianRunGapDays + suggestAdditions shape, rebuildSchedule statuses + recovery decoration, exerciseHistory, nextTargets, goalProgress (strength + cadence w/ dedup), proposeWorkoutWeek, all four histories, weeklyUse, expiring/use-soon. Every expected value hand-computed in comments — this file is the eval set changes run against; a reader change that shifts behavior lands RED here.
7. **Nothing breaks; docs delta.** Full suite green, tsc clean. DATAFLOW: PantryAsserted payload row + propagation ("assert expiry → expiring chips → use-soon"), a NEW consumption-view line (none exists to toggle — finding 1), history readers noted in presentation contracts; WORKPLAN P3 note (consumption/expiry data layer pulled forward; matching/calorie/profile UI stay).

**Non-goals.** Shelf-life inference/defaults tables (invention; revisit with a sourced dataset in P3 catalog work). Expiry on inflow lines or LineItem changes (ripples through orders/cook snapshots; assertion-only v0). Waste tracking events ("threw it out" — a future explicit assertion kind). Notifications. Any UI. Auto-scheduling expiring meals (proposer stays goal-driven; use-soon is data). LLM anywhere. Calorie/macro nutrition. Auth.

**Orientation (compact, in-session).** Pantry fold: assert-replaces / inflow-sums-or-degrades / cook-subtracts-deletes-at-zero (lib/pantry.ts:23-107); PantryItem is the view row; viewReplace writes columns explicitly — new column needs DDL + INSERT change; migrate() CREATE-only (db.ts) → guarded ALTER is new, document swallow-pattern (memory lesson: guard via catch on "duplicate column"). parseAssertion whitelist (pantry.ts:117-146). parseLineItems whitelist untouched (no LineItem change). Replenisher placement precedent for in-context suggestions (cart route :76-89). latest-per-external_id idiom: recovery view + goals countableSessions — history readers reuse the shape. localDate mandatory for day bucketing. listRecipes returns summaries; use-soon needs plans → getPlans on cookbook ids (small N). cooksLeft (lib/fullness.ts) reads RecipeCooked via readEvents — consumption reader is a sibling. No history endpoint exists; /api/history is new. Golden fixture: replenish.test.ts + schedule.test.ts envelope-builder idioms; monotonic event ids keep fold order deterministic.

**Creativity beat.** Alternatives: (1) shelf-life defaults table for auto-expiry — rejected: invented facts on food safety, exactly what precision-honesty forbids; (2) full waste/expiration event loop (ThrownOut events, waste stats) — deferred: needs the explicit-assertion UX first. 10x: expiring items steering the P6 draft composer ("schedule salmon Tuesday, it expires Wednesday") — the use_soon data IS that input, composer comes with P6. Simplest form: one optional field, four pure readers, one fixture file.

**Decomposition.**
1. Expiry: contract + parseAssertion + fold carry + guarded ALTER + view write/read + rebuild invariant + /api/pantry `expires`/`expiring` (criteria 1-2).
2. Use-soon: reader + /api/pantry + /api/cart `use_soon` (criterion 3).
3. Consumption: weeklyUse + /api/pantry `weekly_use` (criterion 4).
4. History: lib/history.ts four readers + /api/history (criterion 5).
5. Golden household + docs delta (criteria 6-7).

**Test strategy.** Fold: expiry set/clear/preserve/delete-at-zero + rebuild identity. Readers: expiring window boundaries (today+7, expired flag), use-soon name matching (normalized, no match → absent), weeklyUse conversion/exclusion/cold-start/window-min-1-week, four histories incl. dedup + date rollover. Golden household per criterion 6.
