# Spec: list-first (grocery pivot + Replenisher v0)

Jake's direction (2026-07-26): no Instacart API key for now. Let the user handle getting groceries however they want and build on top of that: make the list, get specific with items (brand preference, sizes), check things off as they go — order or in store. Plus: some learning now — the list should use consumption history, the meal schedule, and stated preferences to suggest the best possible list.

**Intent.** The shopping list becomes the primary grocery execute mode, and the app starts learning how the household shops. Four behavior changes: (A) an in-store run is a real order — it appears in order history, survives page reload, supports un-check, and lands in the pantry as one confirmed batch; (B) each ingredient can carry a stated preference ("90/10 Angus, 1 lb tray") that shows on every future list; (C) building a list records the week's plan in the diary; (D) the list opens with suggest-only replenishment chips ("eggs — you'll likely run out before your next run") derived deterministically from cook history, grocery-run cadence, and the planned week. No LLM anywhere; suggestions are proposals, never pantry truth.

**Acceptance criteria.**
1. Choosing "Shop in store" on /week writes `OrderPlaced {rail:"instore", items}` (no url) via a real `Rail` implementation; the run appears on /orders as an open in-store run. Instacart stays a rail but its execute option is hidden when `INSTACART_API_KEY` is unset (the UI can no longer reach the 503).
2. Checkoffs during a run toggle freely (check and un-check) and write NO events; state persists in the browser keyed by the run's `order_event_id`, so a reload or phone-pocket resume shows the same checks. A "Got everything" action checks the whole list in one tap; an open run left unsettled surfaces a banner on /week and /orders ("Finish your run? N items checked") opening a quick review that settles it (grill Q1). "Done shopping" writes exactly ONE `PantryInflow {items: checked subset, via:"checkoff", order_event_id}`; the pantry updates through the existing fold; /orders shows the run settled with bought vs skipped visible. Existing-code gates (reviewer findings 1-2): `listOrders`'s settled logic matches only `via:"delivery"` (lib/rails.ts:29-34) — it must also settle on `via:"checkoff"` inflows referencing the order; and the "Mark delivered" reconcile affordance (app/orders/page.tsx:57) must be hidden for `rail:"instore"` orders, else a click writes a spurious delivery inflow of the full requested items. This supersedes P1's one-event-per-checkbox behavior (recipe-groceries-mvp criterion "aisle checkoff IS the reconcile") — the reconcile is now the single Done batch, same shape as delivery reconcile.
3. A preference set on an ingredient (structured `{brand, size, note}`, each optional — Jake's call at grill, enables future UPC/product joins) writes a `PreferenceSet` event and a `prefs_view` row in one transaction (same pattern as pantry: the event is truth, the view is cache); wipe `prefs_view`, refold → identical. Every subsequent list render joins the note onto matching lines by normalized name; the note is editable from the list and during a run.
4. Building a shopping list writes `WeekPlanned {library_ids, titles}` (titles snapshotted like RecipeCooked) — the planned-week signal, nothing else ships with it (no plan-editing UI).
5. Replenisher v0, pure functions over the log: run cadence = median gap in days between settled runs, one event per run (an `OrderPlaced` counts once, at its settling inflow's ts; an orphan inflow with no order counts once) — an instore run's OrderPlaced + checkoff inflow must never double-count; per-item usage from RecipeCooked history (the `cooksLeft` math) + the latest `WeekPlanned`'s recipes. An item projected to run out before the next expected run yields a suggested line on /week with a plain-English reason — in-context only (the list-build screen; suggestions never interrupt another surface), one-tap accept with an editable pre-filled qty (typical purchase amount), one-tap dismiss; a dismissed item stays silent until after the next settled run (grill Q2). Accepting adds the line; each suggestion writes `SuggestionMade` and its outcome writes `SuggestionResolved {outcome: "accepted"|"dismissed"}` — the suggestion/response pair WORKPLAN froze in P1 gets defined now.
6. Cold-start honesty: fewer than 2 prior runs → zero suggestions (no invented cadence); an item with no compatible cook history → no projection for it; suggestions never write pantry state (suggest-only rule, CLAUDE.md).
7. Docs delta lands with the code: WORKPLAN rails row + `:73` Matcher-channel claim (checkoff run reconcile becomes the primary requested-vs-actual channel), PRODUCT.md Phase-1 wording, recipe-groceries-mvp supersedes note for criterion 2's behavior change.

**Non-goals.** Product catalog / product search (no data source; IDP parked — email Instacart in parallel). Store-layout / aisle ordering (P3, needs store data that doesn't exist). Goal/macro alignment of suggestions (needs the P3 profile; no goals data exists). LLM anywhere in this spec — Replenisher v0 is deterministic; the LLM Matcher stays P3. Brand/size entering pantry identity (prefs are list-layer; the fold still keys on ingredient name). Editing/viewing the persisted week plan (P5-6 planner). Push notifications (in-app chips only). Removing the Instacart rail (demoted, not deleted).

**Orientation (compact).** /week is a phase machine (`picking → building → list`, app/week/page.tsx:7-10); list edits live only in React state; in-store checkoff posts one inflow per checkbox with no `OrderPlaced`, no undo (checkbox disabled once bought, :163), state lost on reload — so today's checkoff is invisible to /orders, cadence, and matcher signals. `Rail` is frozen as `buildCart(items) → {url?, cart_id?}` (contracts.ts:66-74); an instore rail returning `{}` satisfies it; WORKPLAN:17 already lists checkoff as a rail backend. `parseLineItems` (lib/cart.ts:55-75) whitelists `{name,qty,unit}` at both API boundaries — new per-line fields die there unless widened (prefs join server-side instead). `migrate()` has no ALTER path — new persistence must be a new table; `prefs_view` follows the pantry_view pattern (event + view same transaction, lib/pantry.ts:160-194). The picked week persists nowhere (grep-verified); UX.md:35 gates the horizon answer on it. `cooksLeft` (lib/fullness.ts) already computes per-cook usage; cadence needs `event.ts` gaps, currently unused. `applyPantryEvent` refolds the whole log per write — criterion 2's single Done batch also removes the O(n²) per-checkbox fold. Undo demand: UX.md:70. Stated-beats-learned: UX.md:76. Deterministic core: WORKPLAN:71. Suggestion/response pair pre-declared but undefined: WORKPLAN:48.

**Creativity beat.** Alternatives: (1) LLM Replenisher now (compose the list with a model) — rejected: violates deterministic-core, no eval data, cold-start hallucination risk; (2) jump to full P3 (profile UI + dials + expiry + matching) — rejected: quadruples scope, blocks real grocery runs behind UI work. 10x-vs-asked: the J5 coach (push notifications, autonomy ladder) — that layer belongs after real usage data exists. Simplest form that works: A+B alone would ship the pivot, but Jake explicitly asked for learning now; C is D's cheapest dependency (one event write), so A→B→C→D with D honest about thin data is the simplest form that satisfies the stated intent.

**Decomposition.**
1. Instore rail + run lifecycle: `instoreRail`, `OrderPlaced {rail:"instore"}` on run start, /orders shows open/settled runs, Instacart option gated on key presence (criteria 1, part of 2).
2. Batch checkoff: local toggle + localStorage persistence keyed on `order_event_id`, single Done inflow, bought-vs-skipped on /orders (criterion 2).
3. Preferences: `PreferenceSet` event + `prefs_view` + rebuild invariant + list/run note UI (criterion 3).
4. `WeekPlanned` event on list build (criterion 4).
5. Replenisher v0: cadence + projection readers (lib/replenish.ts), suggestion chips on /week, `SuggestionMade`/`SuggestionResolved` contracts (criteria 5-6).
6. Docs delta (criterion 7).

**Test strategy.** Pure-function tests: cadence median (0/1/2/n runs, irregular gaps, instore run counted once not twice), projection math (convertible units only, cold-start absences), prefs fold + rebuild invariant, suggestion event pair shapes. Route tests stay thin; live-verify drives a full run: build list → start instore run → check/un-check → reload persistence → Done → pantry + /orders + cadence all observed. No LLM calls anywhere — zero API cost.
