# Spec: planner-composer (backend-complete workstream 4)

Branch `feat/planner-composer` off `feat/retraction-ladder` (PRs #20-23 open; stacked — PR base = `feat/retraction-ladder`).

## Intent

The app greets you with next week already drafted: meals from your cookbook picked by rotation and calorie fit, workouts as the next leg of your program, sleep and mind slots — a full 4-lane week you edit and approve instead of a blank page (UX.md:86, "editing a good draft"). The draft is alive: it recomputes from the current diary on every read, and a stale draft pair is superseded, never left dangling (UX.md:47 "churn in a draft is free"). One meal swaps without touching the rest of the week (`scope:"slot"` exchange). Deterministic core composes candidates; the LLM only picks among them (WORKPLAN.md:71); everything flows through the suggestion pair, and applying stays the user's POST (suggest-only intact).

## Acceptance criteria

1. `GATES.plan_draft` tightens from the provisional frame check to `checkProposedDays` (contracts.ts:248's "provisional until the planner lands" — the planner is landing). Slots missing lane/title now 422 through the gate.
2. The pair learns supersession: when `logSuggestions` finds an OPEN pair with the same identity but a drifted payload, it appends `SuggestionResolved {outcome:"superseded"}` for the old pair before minting the new one — for every kind (repair drift leaves stale opens today too). `readSuggestionState`'s outcome dispatch becomes an EXHAUSTIVE 3-way (its current else-catch-all would silently route superseded into `dismissed`, suggestions.ts:289-295) and returns a fourth bucket `superseded`. Regression pins required for all four dismissed-bucket readers: a drift-superseded ease pair must NOT silence future ease advice for that slot (recovery.ts:66), same for next_target (workouts.ts:156), repair options (repair.ts:326), and autonomy dismissed counts (autonomy.ts:90). `plan_draft` identity becomes `plan_draft:${scope}:${anchor}` where anchor = week_start (week), date (day), or slot_id (slot) — NOT the days blob (identity is the thing proposed about, drift is payload, the nutrition_adjust:week_start precedent).
3. `GET /api/plan/draft` returns `{draft: {days, reason}, suggestion_id}` for NEXT Monday's week: meal lane (one dinner slot/day, recipes from MY library, least-recently-cooked rotation, never-cooked newest first), workout lane via the existing `proposeWorkoutWeek` (program/deload-aware), one sleep slot/day, two mind slots/week (Tue/Thu "Journal"). Empty library lanes degrade honestly (no meals in library → no meal slots + reason says so). Writes NO `SchedulePlanned`; logs exactly ONE open `plan_draft` pair (scope week, identity per week_start).
4. Living draft: a second GET with an unchanged diary returns the SAME suggestion_id (byte-identical recompute reuses the open pair). A diary change that alters the draft (e.g. cooking tonight's rotation pick) yields a NEW suggestion_id and the old pair reads `superseded` — never a second open week-draft.
5. Deterministic energy fit: with an active nutrition goal and macro-carrying recipes, meal candidates order by closeness to the per-meal calorie envelope `week_target / meals_being_drafted` — the drafted week is NEXT week, whose consumed is structurally 0, so the envelope is a constant; the CURRENT week's consumption must never leak into next week's plan (leaking it would make tonight's dinner shrink next Thursday's). Ties by rotation order. No goal or no macros → rotation order alone.
6. Recovery tuning: when the latest recovery score is red (< RED_ZONE), the drafted week drops to `ceil(base/2)` sessions where base is the program-aware count — and the halvings do NOT stack: a red week that is also a program deload week halves ONCE (min of the two rules, `ceil(per_week/2)`, never a quarter). The reason names whichever rule fired; the LLM pick stage may NOT add sessions back.
7. `POST /api/plan/exchange {slot_id}` (meal slots in the CURRENT plan — the repair precedent: proposals about the locked week ride the pair, and only the user's accept-POST changes anything): returns a `scope:"slot"` plan_draft whose `days` are the full current snapshot with exactly that slot's meal swapped to the next rotation candidate (slot_id dropped on the swapped slot — new identity; every other day/slot byte-identical). Unknown slot_id → 404; non-meal slot → 422; library has no alternative → 422 with reason. Accepting stays two-step: the client POSTs `/api/schedule` with the draft days (J9 pattern).
8. LLM picks only: `lib/plan-pick.ts` (repair-score idiom — static cached rubric, injectable ModelCall, first-JSON-object parse): the model receives per-slot candidate recipe ids (top 3 by AC5 order) + typed context (budget, recovery, program phase) and returns `{picks: {"<date>": "<library_id>"}}`; every pick must name a supplied candidate or that slot falls back to candidate #1. Fires only when the draft pair is fresh (not on steady-state reuse); no key and no injection → candidate #1 everywhere.
9. Journey evals: new `tests/journeys/journey-draft-week.test.ts` demand-first covering 3-4-7 + accept-apply + dismiss-silences-the-week + the Wednesday-swap-doesn't-wipe-Thursday full-replacement pin + hostile gates. Existing J1/J9 pins stay green (`/api/schedule/propose` untouched).

## Creativity beat

Alternatives: (a) model composes the whole week directly from context (freeform JSON week) — rejected: violates deterministic-core, unverifiable output, identity/nondeterminism breaks pair reuse; (b) event-push recompute (a worker recomputing drafts when events land) — rejected: adds infrastructure for zero UX gain; recompute-on-read IS the living draft (reads follow events). 10x version: constraint-solver composition (macro targets, prep-time budgets, variety penalties, pantry consumption optimization) — the data isn't there yet and the LLM-pick seam is where that judgment lives for now. Chosen: deterministic candidate generation + narrow LLM pick + pair supersession. Simplest form that works: rotation + envelope-fit ordering, one pick call per fresh draft, identity per anchor + drift supersede. Supersession is the one pair-machinery change and it fixes a latent leak for every existing producer.
