# Spec: recipe-groceries-mvp (Phase 1 — Food loop MVP)

Vision, market, moat: `PRODUCT.md`. User model and journeys: `UX.md`. System map and phase wiring: `WORKPLAN.md`. This spec covers Phase 1 only: the smallest working version of the loop, shipping journeys J1 (URL intake), J3 (review and order), J4 (cook it), plus the pantry math underneath. Single household (Jake), no accounts, web only.

**Intent.** A web app where you paste recipe URLs, it extracts structured recipes (ingredients + distilled instructions), you pick meals for the week, it diffs ingredients against your pantry and produces a one-click Instacart cart link; cooking ("I made this") and order arrival update the pantry. Under the hood, phase 1 lays the event spine and the three frozen contracts (event envelope, StructuredPlan, Rail interface) that every later phase reads from. It must *feel* like the loop: save → pick → order → cook → pantry moves.

**Acceptance criteria.**
1. Paste a recipe URL → structured recipe (ingredients with name/qty/unit, distilled numbered steps, servings, time) appears for review within ~15s; low-confidence fields are visibly flagged; user edits then saves to Library.
2. Select 1-N saved recipes for the week → combined shopping list: duplicate ingredients aggregated, pantry-stocked items excluded, each line editable.
3. Two execute modes from the same list, user's choice: **(a) Order** → opens an Instacart shoppable page (IDP Create Shopping List Page, dev key) whose item list matches the computed missing-items list exactly (verified item-for-item in the live test, not just "a cart opened"); **(b) Shop in store** → the list becomes a checkable shopping list; checking an item off records it as bought (pantry inflow). The loop works end-to-end with no external API via mode (b).
4. Delivery path: marking the order delivered runs a quick reconcile ("anything subbed or missing?") and adds actuals to pantry. In-store path: aisle checkoff IS the reconcile.
5. Cook mode: step-at-a-time view with big type; "I made this" decrements the recipe's ingredients from pantry and logs the cook.
6. Pantry page: add/edit/remove items (each an explicit user assertion); state survives restarts.
7. Every state change in 1-6 lands as one event in the `events` table with the frozen envelope (`event_id, household_id, user_id?, type, ts, source, payload, schema_version, precision` — `user_id` optional, single-user in P1); pantry view is rebuildable from the log alone. The rebuild test is written in unit 1 and **extended in units 3, 5, and 6** as each new event type lands (`PantryAsserted`, `OrderPlaced`, delivery inflow, `RecipeCooked`); criterion is met only when the final rebuild covers all P1 event types.

**Non-goals (Phase 1).** Video/TikTok extraction, share-sheet/Shortcut intake, cook-mode timers (P2 polish). Drafted week, meal modes (prep/special/out), calorie budget + smoothing, expiry logic, matching learning, profile UI, notifications, store-personalized list organization (layout/preferences/macro priorities — P1's in-store list is a plain checkable list) (P3). Auth, households beyond the hardcoded one, Kroger rail, payments (P4). Workouts, program engine, repair engine (P5+). Wearables (P6). Any social (P8). Automated checkout (no compliant API exists). Quantity-precise pantry math (rough counts + `precision` field, per UX.md's dial).

**Orientation findings.** Greenfield; no prior consumer/commerce art in Jake's history. Closest shipped stack: agentdiff (Next.js App Router on Vercel Hobby). Deploy gotchas runbook: wiki/coding-log/failures/agentdiff/2026-05-20-render-vercel-deploy-gotchas.md. Binding memory lessons: first live API call = multi-hypothesis curl probe; decode OAuth scopes before trusting 403s; LLM parsing = cached static rubric + tolerant fence-stripping parse + enum validation + deterministic fallback; DB field additions default on read. Rails research (verified 2026-07-24): Instacart IDP = link generator only, product names in / shoppable URL out, no SKU, dev key immediate, production key ~30-40-day business-gated approval, affiliate via Impact.com; Kroger = only self-serve cart-write, no checkout; no compliant third-party full checkout anywhere.

**Stack.** Next.js App Router, single deploy surface, Vercel Hobby. Turso (libSQL): `events` + `library` + `pantry_view` + `profile` tables (event-sourced, per WORKPLAN.md § Phase 1 schema implication). Claude Haiku via /v1/messages for extraction (cached static rubric). Instacart IDP dev key; production application submitted in parallel during unit 7.

**Decomposition (commit-sized units, in order).**
1. **Scaffold + spine:** Next.js app, Turso schema (events, library, pantry_view, profile), event-write/read helpers, pantry rebuild function + test, health check, Vercel deploy skeleton.
2. **Recipe ingest:** URL fetch → Claude extraction → StructuredPlan v1 (recipe subtype); eval fixtures on 5 real recipe sites (incl. NYT Cooking paywall behavior); review/edit UI with confidence flags; save to Library.
3. **Pantry CRUD:** page + API; every mutation a `PantryAsserted` event; view rebuilt from log.
4. **Cart builder:** week picker (multi-select saved recipes) → ingredient aggregation (unit-aware merge where trivial, dumb-concat otherwise) → pantry diff → editable shopping list.
5. **Execute modes:** Rail interface; in-store checkoff list first (no API: checked item → bought/inflow event), then Instacart rail (curl-probe IDP live before code; "Order" flow → shoppable URL; `OrderPlaced` event).
6. **Close the loop:** delivered + reconcile flow → pantry inflow events; cook mode UI; "I made this" → `RecipeCooked` + decrements.
7. **Ship:** production deploy, IDP production-key application package, README.

**Test strategy.** Vitest. Unit tests on pure logic (aggregation, diff, pantry rebuild). Eval fixtures for extraction (golden set): structural assertions on ingredients (schema-valid, count bounds, no hallucinated ingredients) AND on steps (step-count sanity bounds, imperative numbered form, not a verbatim paste of source prose). Failure-path fixture: a no-recipe-content fetch (real bot-block page; NYT Cooking turned out to ship its full recipe in public JSON-LD, so it is a success fixture instead) must produce a graceful "couldn't extract" outcome with zero hallucinated content — that is its pass condition. One live integration test per external surface (IDP call, Claude call) marked integration, run manually; the IDP live test asserts item-for-item match between the diffed list and the created shoppable page. Rebuild-from-log test written unit 1, extended units 3/5/6 (criterion 7). Live end-to-end at unit 7: real recipe → real Instacart cart in a browser.

**Frozen contracts produced here** (change = version bump, never in-place): event envelope, StructuredPlan schema, Rail interface, suggestion/response event pair (defined now, first used P3).

## Superseded (2026-07-26, spec list-first)
- Criterion 3(b)/4's in-store behavior: per-checkbox pantry inflow ("aisle checkoff IS the reconcile") is replaced by the list-first run — `OrderPlaced {rail:"instore"}` at run start, free check/un-check in the browser, ONE `PantryInflow {via:"checkoff", order_event_id}` batch at Done. `listOrders` "delivered" became "settled" (any inflow referencing the order).
- Criterion 3(a)'s Instacart mode is demoted behind key presence (no IDP access yet); the 503 path is unreachable from the UI.
