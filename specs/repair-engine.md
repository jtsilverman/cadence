# Spec: repair-engine v0 (deterministic workout-repair menu on the suggestion pair)

Workstream B of the A→D roadmap. A (suggestion-pair-v2, PR #17) built the seam this fills: the `repair` kind exists in the `SuggestionMade` union with a provisional payload and a frame-only parse gate; nothing emits it. This spec ships the first producer.

## Intent

When you skip a workout, the system answers immediately. A `SlotSkipped` on a workout slot in the current (Monday-start) week triggers a deterministic repair menu — the UX.md:49-55 five-option menu, v0 subset: **shift** (makeup slot on a free remaining day), **double_up** (makeup on a day that already has a workout, only when recovery is not red), **consolidate** (merge into the next planned session — the slot's title is amended `"{existing} + {missed} (merged)"`; reduced-volume math waits for P5 progression, the reason line says so), **drop** (absorb the miss, record it) — scored by documented rules (day-of-week position, free/busy remaining days, latest recovery), one option marked `recommended`. This is the workout menu Jake named 2026-07-27 (shift / double up / merge-replace); consolidate is the merge, thin until structured volume math exists. Each viable option is one `SuggestionMade {kind: "repair"}` on the existing pair, so accept/dismiss accrues as training data for the P5 LLM scorer. The skip receipt (POST /api/log) carries the menu in the same response — "repairs the moment the event lands" (UX.md:46) with no push infra. Accepting stays suggest-only: the proposal's `days` is a full replacement snapshot the user applies via their own POST /api/schedule; the engine never writes the plan.

**Decisions (surfaced, flag if wrong):**
- **Deterministic v0.** WORKPLAN:71 puts repair *scoring* at the LLM boundary (P5 proper). v0 ships the deterministic menu on the same contract — the same breadth-first move as nextTargets and the week proposer; the LLM scorer later swaps in behind the identical pair, with accumulated choice data to learn from.
- **double_up gates on "not red", not "green".** UX.md:51 says green recovery only; no verified green threshold exists (RED_ZONE=34 is itself marked unverified). v0 uses `score >= RED_ZONE or unknown`; documented at the constant.
- **Trigger is the explicit skip only.** No past-pending "missed" inference (a never-logged past slot still reads `planned`); that's a different feature (nudge), not repair.
- **Always propose, even drop-only.** A late-week red-recovery skip yields a menu of just `drop` — the accepted drop pair IS the "record it, E adjusts" record (UX.md:54), and the choice is still training signal.

## Acceptance criteria

1. **Pure menu scorer.** `lib/repair.ts` computes, from (resolved schedule days with statuses, recovery-by-date, household-local today): for each `lane: "workout"` slot in the current Monday-start week with `status: "skipped"`, the viable options with target dates and one-line reasons, exactly one marked `recommended`. Rules, each pinned by a test:
   - `shift` viable iff a remaining day of the current week (today through Sunday, household-local) holds no workout-lane slot at all; target = earliest such day. (Any-status deliberately: a done workout can only sit on today, and shifting onto a day you already trained is a double-up in fact; a day with a skipped workout is not a fresh day either. Diff reviewer surfaced the original "no *planned* workout" wording as diverging from this — wording fixed, behavior confirmed intended, pinned by test.)
   - `double_up` viable iff a remaining day holds a still-`planned` workout slot AND the latest known recovery score (on or before today) is not red (`>= RED_ZONE` or absent); target = earliest such day.
   - `consolidate` viable iff a remaining day holds a still-`planned` workout slot (no recovery gate — the merge is the gentler makeup); target = earliest such day; the proposal amends that slot's title to `"{existing} + {missed} (merged)"` (same slot_id, so its logs stay attached).
   - `drop` always viable.
   - `recommended`: red recovery or ≤1 remaining day → `drop`; else `shift` if viable; else `consolidate` if viable; else `drop`. (`double_up` is offered as an alternate, never the pick — UX.md:51 reserves it for high-priority sessions, a concept P5 owns.)
   - Skipped meal/sleep/mind slots produce nothing (UX.md:57). Skips outside the current week produce nothing (last week's miss ages out).
2. **Deterministic full-snapshot payloads.** Each option's `days` is the complete replacement plan (latest snapshot's days, plus for shift/double_up one makeup slot — same title and lane as the missed slot, target date, **no slot_id**; ids are minted by parseScheduleDays at the user's accept-POST). `drop`'s `days` is the current snapshot unchanged. Payloads are deterministic (no minted ids, no timestamps) so identical recomputes are byte-identical.
3. **Producer on the pair.** `attachRepairSuggestions` (the attachEase idiom): GET /api/schedule for a household whose current week holds a skipped workout slot writes idempotently one `SuggestionMade {kind: "repair", missed_slot_id, option, days, reason, recommended?}` per viable option — identity key `repair:${missed_slot_id}:${option}`, `precision: "estimated"`, `source: "web"` — and the response carries the proposals (suggestion_ids attached). Repeat reads write nothing; two concurrent reads serialize through the suggestion write chain to one Made per option (pinned by a concurrency test). A plan edit that changes the computed `days` mints fresh Mades (payload drift, existing logger behavior).
4. **The skip receipt carries the menu.** POST /api/log with `{kind: "skip"}` on a current-week workout slot returns the schedule days AND the repair proposals in the same response (the log route's receipt goes through the same payload builder as /api/schedule; ease attach rides along unchanged).
5. **Dismissal windows.** Dismissing `repair:${slot}:${option}` silences that option for that slot (not the siblings). An *accepted* repair for a slot silences ALL repair proposals for that slot (the producer's predicate; no re-propose even though the skip status persists after the plan changes). **Read-path extension (reviewer finding):** `readSuggestionState` currently discards accepted rows (suggestions.ts:198-199 pushes only open/dismissed) — it gains an `accepted` array (additive; existing producers consume `dismissed` only, unaffected). Both windows pinned by tests. Sibling opens left behind by an accept are not auto-resolved (named debt, the future inbox's concern).
6. **Contract finalized + gate tightened.** `RepairSuggestion` gains `recommended?: true`. **Type decision (reviewer finding):** `days` cannot stay `SchedulePlannedPayload["days"]` — `ScheduleSlot.slot_id` is required (contracts.ts:96) and every schedule consumer assumes it, so a makeup slot without an id wouldn't compile. A new `ProposedDays` type (same shape, `slot_id` optional on slots) is defined for proposals; `RepairSuggestion.days` and `PlanDraftSuggestion.days` both point at it (nothing emits plan_draft; its gate stays frame-only). `GATES.repair`'s frame-only `checkDays` is replaced with real slot validation (parseScheduleDays semantics, minus the mint). The provisional-shape comment at contracts.ts:181-183 drops repair. Superseded suggestion-pair-v2 test literals updated RED-first.
7. **Resolve unchanged.** POST /api/suggestion resolves a repair Made exactly like any kind (server-side join, Resolved carries `kind: "repair"`). No accept-side effects: applying the repair is the user's explicit POST /api/schedule with the proposal's `days`, and doing so end-to-end (accept → POST days → grid shows makeup slot; skipped slot stays visible with its skip status) is live-verified.
8. **Golden household.** The existing diary already stages it (w-fri workout skipped 2026-07-25, today Sunday 2026-07-26, w-sun planned today, recovery 30 red): pins exactly two repair Mades — `drop` with `recommended` (red recovery + last day) and `consolidate` targeting w-sun (busy day, no recovery gate); `shift` (no free day) and `double_up` (red) absent — idempotent across reads, then `drop` resolved accepted with `kind: "repair"`. Hand-computed expectations, never output-fitted.
9. **Nothing breaks.** Pantry rebuild invariant green with repair events interleaved; existing ease/next_target/replenish suggestion tests green; /week grocery chips untouched.
10. **Docs delta.** DATAFLOW.md:41 SlotSkipped read-by updated (repair engine shipped v0, no longer "planned P5"); WORKPLAN.md:62/67 note (deterministic repair menu v0 pulled forward; LLM repair scoring + consolidate/redistribute + adjacency/priority inputs stay P5 proper); DATAFLOW invariant 3 wording already covers suggest-only (no change beyond the read-by row).

## Non-goals

- **LLM repair scoring** (P5 proper; v0 is rule-based on the same contract).
- **redistribute** — needs key-set extraction from structured sessions (P5); the enum keeps it, no producer emits it. Consolidate's reduced-volume math likewise waits for P5; v0's consolidate is the title-merge only.
- **Meal and diet repair** (Jake's 2026-07-27 direction: makeup meals / cut-down-through-chosen-snacks after a skipped meal or a diet overshoot). Not buildable yet: there is no prescribed-diet or calorie/macro concept in the data (workstream C), and UX.md:57's signed-off schedule-spine decision currently says meals never repair. This lands as part of C (nutrition) — where "prescribed" becomes computable — and revisits UX.md:57 there. Queued as a follow-up, not silently absorbed here.
- **Auto-apply / autonomy ladder** (UX.md:46's "trivial reshuffles auto-apply" contradicts the current suggest-only invariant, DATAFLOW.md:108; the ladder is a Jake decision for a later phase).
- **Accept-side schedule mutation.** Accepting a repair writes only the Resolved event; the plan changes only via the user's POST /api/schedule.
- **Past-pending "missed" detection** — only explicit SlotSkipped triggers repair.
- **Sleep/mind repair.**
- **Sibling auto-resolve on accept** (resolve stays kind-dumb; producer-side silencing only).
- **Adjacency and session-priority scoring inputs** (UX.md:55) — no hard/easy or priority concept exists yet (P5's block periodization).
- **No new `source` value; no UI surface** (the menu is API-complete; its affordance lands with the schedule grid / Today UI, schedule-spine units 2-3).

## Creativity beat

- **Alternative 1: LLM scorer now.** Rejected: no choice data to learn from, deterministic-core rule (WORKPLAN:71), and the pair contract is identical either way — v0 accumulates exactly the training data the LLM scorer needs.
- **Alternative 2: one Made carrying the whole menu** (pick + alternates in one payload). Rejected: the resolution loses which option was chosen — the accept/dismiss-per-option trail is the training signal; per-option Mades cost only an identity-key change.
- **10x-vs-asked:** the full autonomy ladder — repeated choices become auto-apply with undo (UX.md:46/55). Needs choice history (which this ships) and a Jake decision to relax suggest-only; P6+.
- **Simplest form that works:** three rule-based options on the existing pair, attached to the reads that already exist, full-snapshot days so accept is a verbatim POST. No new tables, no new event types, no scheduler.
