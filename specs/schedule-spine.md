# Spec: schedule-spine (the full schedule, top to bottom, before prod)

Jake's direction (2026-07-26): broad initial system first, top to bottom, then flesh out. Build the entire schedule — meals, sleep, meditation, journaling, workouts — before wiring to Vercel. Whoop + Garmin are the wearables to integrate first (own spec, research in flight).

**Intent.** The product stops being food-only. /week's picker becomes a 2-week schedule grid (Monday-start) holding typed slots across the four lanes — meals from the cookbook, workouts (structured or loose: class, sauna, yoga), sleep, mind (meditation/journaling) — and a new /today screen is where you live: today's slots, one tap to log done or skip, each tap writing a typed event to the diary (`SessionLogged`, `SleptLogged`, `JournalEntry`, `SlotSkipped`; meals keep `RecipeCooked` through cook mode). The shopping list stops asking "what are you cooking?" and builds itself from the current week's meal slots, with true buy quantities (needed − on-hand). Wearables get their seam — the sleep/recovery event contracts carry `source` and `precision` so Whoop/Garmin ingesters later write the same events a human writes today — but no OAuth in this spec. Everything here is deterministic; the agent that *composes* the schedule comes later, with data.

**Acceptance criteria.**
1. **Schedule grid.** /week renders a 2-week Monday-start grid (this week + next). Add a slot to any day — meal (picked from the cookbook), workout (title, e.g. "squat day" or "yoga class"), sleep (a nightly intention, e.g. "10:30 bedtime"), mind (e.g. "meditate", "journal"), custom title — remove it, move it to another day. Slots are loose-per-day: no clock times. Payload shape (reviewer finding 1): `SchedulePlanned {days: Array<{date: "YYYY-MM-DD", slots: Array<{slot_id, lane: "meal"|"workout"|"sleep"|"mind"|"custom", title, library_id?}>}>` — absolute ISO dates (never weekday labels), meal slots carry `library_id`. Every edit writes one `SchedulePlanned` snapshot event (latest wins, the `WeekPlanned` pattern); `slot_id`s are minted once and survive later snapshots, so logs never orphan. Concurrent-edit race (finding 4): snapshot writes serialize through an in-process chain (the pantry-write idiom, lib/pantry.ts:157-178); cross-instance last-write-wins is accepted for a single household, same as pantry. The grid is a pure reader over the log: same events → same grid, no new tables.
2. **Today.** /today lists today's slots. Tapping "did it" writes the lane's typed event and the slot renders done only after the write returns (UX.md:71, no optimistic UI); "skip" writes `SlotSkipped`. A meal slot offers quick "did it" (writes the existing `RecipeCooked` via /api/cook — pantry decrements as always) or opens cook mode for the step-through; either way `RecipeCooked` is the done-marker; the schedule reader joins `RecipeCooked` on `library_id` + the cook event's ts date (absolute slot dates make cross-week collisions impossible; finding 2); N same-day duplicate slots of one recipe resolve in slot order, one cook marks one slot. A skipped meal writes `SlotSkipped` only — pantry untouched, no re-slotting (UX.md:57).
3. **Typed logs.** `SessionLogged {slot_id?, title, kind: "structured"|"loose", note?}` (a loose class/sauna/ice-bath counts without progression, WORKPLAN P5); `SleptLogged {date, quality: "rough"|"ok"|"great", hours?}`; `JournalEntry {text, slot_id?}`. All three can also be logged from /today WITHOUT a planned slot (you did a workout that wasn't planned; you journal unprompted). `SlotSkipped {slot_id, lane}`.
4. **Wearable seam.** `SleptLogged` and new `RecoveryLogged {date, score?, hrv?, resting_hr?}` are the ingest contracts: envelope `source` says who wrote it ("web" now, "whoop"/"garmin" later), `precision` says how much to trust it ("estimated" for manual quality-taps, "exact" for device data). No consumer branches on source yet; the Whoop/Garmin OAuth ingesters are the next spec (research pending, incl. Garmin's business-application gate).
5. **List from the plan.** "Build shopping list" reads the CURRENT week's meal slots (the cart builds from the standing plan — no more picker phase); `SchedulePlanned` supersedes `WeekPlanned` (writer deleted, old events ignored). Buy quantities become true amounts: a line's qty = recipes' need − pantry on-hand where units convert (0.8 lb held, 2 lb needed → buy 1.2 lb); fully covered items move to stocked; cross-dimension stays the honest full-need line on toBuy with a "have some" flag (no density math). New contract (finding 3): toBuy = lines with remaining need or unconvertible coverage; stocked = fully covered lines. This deliberately rewrites `diffAgainstPantry`'s name-presence contract — the lib/cart.ts:77 comment and two tests ("pantry match is by name only — a stocked name excludes every unit line"; the flour cup/g exclusion case) are superseded, RED-first. Replenisher suggestions unchanged on top (plan-shortfall chips largely absorbed by true quantities; staple chips remain).
6. **Nothing breaks.** Existing folds ignore the new event types (pantry rebuild invariant still green); the shopping-list → run → done → pantry loop works end-to-end from the new grid; /orders, prefs, suggestions all as shipped in list-first.
7. **Docs delta.** WORKPLAN sequencing note (P5/P6/P7 slot-and-log skeletons pulled forward, pre-prod, per Jake 2026-07-26; agents/extraction/wearable-OAuth stay in their phases), UX.md screens list gains Today, PRODUCT.md § Schedule marked v0-shipped-thin.

**Non-goals.** Lock/approval ceremony, living draft, drafted-week proposals (P6 Planner — needs data + program engine). Repair engine and progression math (P5). Workout video extraction and the StructuredPlan workout subtype (P5; parseExtraction hard-rejects non-recipe shapes — its own task). Wearable OAuth/webhooks (next spec, post-research). Journaling prompts, mood trends, meditation content (P7 Coach). Calorie/macro anything. Sleep targets from a profile (no profile UI yet; sleep slots are hand-typed intentions). Push notifications. Time-blocked slots (loose-per-day, decision surfaced 2026-07-26). Multi-week program skeletons (E).

**Orientation (compact).** /week is `picking → building → list` + RunScreen (app/week/page.tsx); the picker half is the documented successor point for the four-lane schedule (UX.md:121 "This week … later: the full four-lane drafted schedule"); the list/run half must stay reachable (only path to OrderPlaced/PantryInflow). `WeekPlanned` (contracts.ts:98) is the only plan-state event: dateless, meal-only, snapshot-wins — `SchedulePlanned` is its dated, laned successor. One-tap-done precedent: `RecipeCooked` via /api/cook (event → fold → pantry line as receipt). All existing folds are filter-in over known types, no exhaustive switches — new event types are silently ignored (rebuildPantry lib/pantry.ts:34-102, fullness, replenish). `source` is an unread free string, every writer hardcodes "web" — the wearable seam is free. `readEvents` has no date filter and events has no type index; scale is fine for one household, noted for later. `migrate()` is CREATE-only — but criterion 1 needs no new table (pure reader). Weeks start Monday (UX.md:47). Two mind slots per WEEK is the UX cadence (UX.md:86) — grid default, not enforcement. Meal-skip is deliberately dumber than workout-skip (UX.md:57 vs :49-55) — uniform `SlotSkipped` + no pantry effect encodes it. Blast radius avoided: no StructuredPlan union (listRecipes has no kind filter — a workout row would leak into the Cookbook; cook-mode assumes steps/ingredients unconditionally).

**Creativity beat.** Alternatives: (1) per-slot CRUD events (SlotAdded/SlotRemoved/SlotMoved) — rejected: three event types + ordering rules vs one snapshot type in the established WeekPlanned idiom; (2) jump to the P6 drafted week (agent proposes, you approve) — rejected: composition without history or a program engine is guessing, and Jake's direction is breadth. 10x-vs-asked: the living draft + repair engine — arrives with data at P6. Simplest form that works: the loose grid + typed logs + today view; lock ceremony, drafts, and agents all bolt onto these same events later ("later phases add readers, not rewrites", WORKPLAN:20).

**Decomposition.**
1. Contracts + schedule fold: `SchedulePlanned`, `SessionLogged`, `SleptLogged`, `JournalEntry`, `SlotSkipped`, `RecoveryLogged`; `lib/schedule.ts` pure fold (latest snapshot + resolution join incl. RecipeCooked-by-library_id+date); tests incl. slot-id stability and unknown-type regression (criteria 1-4 contracts, 6).
2. /api/schedule GET/POST + the /week grid UI (2-week Mon window, add/remove/move, cookbook picker for meal slots) (criterion 1).
3. /today + POST /api/log (session | sleep | journal | skip) + receipt-rule UI + cook-mode link/join (criteria 2-3) + nav.
4. List-from-plan: /api/cart reads current-week meal slots; quantity-aware diff in lib/cart.ts (needed − on-hand via convert, drop covered, cross-dim honest); `recordWeekPlanned` deleted (criterion 5).
5. Docs delta (criterion 7).

**Test strategy.** Pure fold tests: snapshot-wins, slot-id stability across edits, per-lane resolution join (RecipeCooked date join, SessionLogged with/without slot, skip), Monday-window math. Quantity-diff tests: convertible subtraction, full-coverage drop, cross-dim fallback, null qty. Regression: pantry rebuild invariant with schedule events interleaved. Live-verify: plan a week (meal + workout + sleep + mind) → /today log each type → grid shows done → build list from slots → run → pantry. No LLM anywhere.
