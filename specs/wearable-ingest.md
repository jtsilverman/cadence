# Spec: wearable-ingest (Whoop direct, v2)

Follows schedule-spine (the contracts seam it fills). Research: `research-wearable-apis.md` (verdict: Whoop direct now — self-serve, free, v2 API, 10-user dev cap no approval; Garmin blocked indefinitely, aggregators absurd at 1-user scale).

**Intent.** The diary starts receiving device truth. Connect Whoop once (OAuth2), and recovery scores, sleep, and workouts flow into the same typed events a human writes today — `RecoveryLogged`, `SleptLogged`, `SessionLogged` — with `source: "whoop"` and `precision: "exact"`, via webhooks (go-forward) and a manual sync pull (backfill + local dev). Recovery becomes readable next to the schedule: GET /api/schedule carries each day's latest recovery and a deterministic advisory flag when a rough-recovery day holds a planned workout — advice as data, no events, no side effects. The suggest-only invariant is sharpened, not violated: devices never touch the *plan* (SchedulePlanned) or pantry; slot *status* is a derived join over logs, and a device log is as good a receipt as a tap (DATAFLOW wording reconciled in the docs delta). No UI beyond a connect link; no Garmin; no agent.

**Acceptance criteria.**
1. **Connect.** GET /api/whoop/connect (WHOOP_CLIENT_ID/SECRET set) → 302 to Whoop's authorize URL with `state` (random, single-use, verified at callback — CSRF gate); /api/whoop/callback exchanges the code, stores tokens in a new `wearable_tokens` table keyed (household_id, provider), and redirects to `/` with a connected flag. Keys unset → 503 at the routes, throw in the lib (the Instacart three-part idiom). Callback with bad/missing `state` or a Whoop error param → honest failure page param, no token write. GET /api/whoop/status → `{connected: boolean}` (a `wearable_tokens` row for (household, "whoop") exists); the connect link + connected badge on / render from it — that row-presence read IS the badge contract.
2. **Single-writer token refresh.** Whoop rotates the refresh token on every use; a lost race permanently bricks the connection. Refresh is compare-and-swap: `UPDATE wearable_tokens SET ... WHERE refresh_token = <the one I used>`; 0 rows affected → another instance rotated first → re-read and use the stored tokens, never a second refresh call with a stale token. In-process calls additionally serialize through a promise chain (the pantry-write idiom). Test proves the race: two concurrent refreshes, one Whoop call total, both callers end holding the same final tokens.
3. **Authed GET with recovery-once.** Whoop API calls attach the bearer token; a 401 triggers one refresh-and-retry, then propagates. 429/5xx propagate with status + body (no invented retry loops; Whoop's limits are 100/min, 10k/day — a solo household never grazes them).
4. **Ingest mapping.** A Whoop recovery record → `RecoveryLogged {date, score, hrv, resting_hr, external_id: "whoop:recovery:<cycle_id>"}`; a sleep record → `SleptLogged {date, quality, hours, score?, external_id: "whoop:sleep:<sleep_id>"}` where quality maps score ≥85→"great", ≥70→"ok", else "rough" (thresholds documented at the mapper); a workout record → `SessionLogged {title: <sport name>, kind: "loose", external_id: "whoop:workout:<workout_id>"}` — no slot_id, never auto-marks a planned slot done (device never writes schedule truth; sleep's date-join is a log-receipt, named intended). All dates through `localDate` (Whoop timestamps are UTC; the night a sleep belongs to = local date of its **end**). Envelope: `source: "whoop"`, `precision: "exact"`, `schema_version: 2` on the three types when payloads carry the new optional fields (`external_id` everywhere, `score` on sleep); existing v1 events and writers unchanged — additive optional fields, readers never branch on version.
5. **Idempotent, latest-wins ingestion.** Whoop redelivers (5 retries/hr) and revises records (scores settle over a morning). `event_id` stays `newEventId()` (sort invariant untouched); identity lives in `payload.external_id`. Before append: read the latest event bearing that external_id — identical payload → skip (no event); changed payload → append (revision). The read-then-append pair races with itself (overlapping webhook redeliveries, webhook vs manual sync) — ingestion serializes through the same in-process chain as tokens; cross-instance residue is a duplicate event with identical payload, cosmetic not corrupting since readers resolve latest-per-external_id (named accepted risk, same class as the pantry chain's concession). Readers that consume these types resolve latest-per-external_id (recovery view; schedule's sleep-slot join unaffected in practice — same date either way). The pantry fold ignores all of it (regression-tested). **A Whoop-ingested SleptLogged auto-marks that date's planned sleep slot done via the existing date-join (schedule.ts:92-95) — explicit, wanted: the device saw you sleep, no tap needed.** Workout events never auto-mark (no slot_id).
6. **Webhook.** POST /api/whoop/webhook verifies the v2 signature (HMAC over timestamp+body with the client secret — exact header names/format probed live at build, not assumed) → 401 on mismatch; on `*.updated` events for recovery/sleep/workout it does the authenticated follow-up GET in-request (payload is IDs only), maps, ingests, 200s. Unknown types 200 no-op (never make Whoop retry what we don't want). `*.deleted` → no-op v0 (diary is append-only; deletion semantics deferred, documented).
7. **Sync.** POST /api/whoop/sync pulls the last 14 days of recovery + sleep + workouts through the same mapper/ingest path (webhooks can't reach localhost; also the post-connect backfill). Returns counts {appended, skipped}. Idempotent: second run all-skip.
8. **Recovery next to the schedule.** `lib/recovery.ts`: latest recovery per date from the log (latest-wins per external_id, then latest per date). GET /api/schedule days gain `recovery?: {score, hrv?, resting_hr?}` and `advice?: "ease"` — set when that day's score < RED_ZONE AND the day holds a planned workout slot. RED_ZONE defaults 34 (commonly-cited Whoop red band 0-33) but is UNVERIFIED in our research file — confirm against Whoop docs during the build's live probe, adjust the constant, document the source at its definition. Pure reader, no events written, no schedule mutation.
9. **Tests + eval.** Mocked-fetch unit tests (token exchange, CAS race, 401-refresh-retry, signature verify, mapper golden cases from captured real API response shapes, idempotent re-ingest, revision append). Integration suite `whoop.integration.test.ts` gated `RUN_INTEGRATION` + tokens present: live profile + recovery GET, shape assertions — the multi-hypothesis probe happens at build time and its captured shapes become the mock fixtures. Regression: pantry rebuild invariant with whoop events interleaved.

**Non-goals.** Garmin (blocked upstream; aggregator ToS unverified — revisit per research file). Any UI beyond a connect link + connected badge on / (grid/Today UI is its own design pass). Suggestion events from recovery (advice is response data only; SuggestionMade/Resolved wiring belongs to the planner/repair phase with a real surface). Strain/cycle/steps ingestion (recovery+sleep+workout only — the three consumers exist). Calorie/energy budget. Webhook deletion semantics. Token encryption at rest beyond Turso's (plaintext column, single household, pre-auth product — named debt for P4). Whoop app approval (>10 users). Background jobs/queues (in-request work only, Vercel constraint).

**Orientation (compact).** Envelope + contracts ready: `RecoveryLoggedPayload` (contracts.ts:128-133) explicitly the ingest contract; `source` free string, all writers hardcode "web" (logs.ts:146); `precision: "exact"` for device data (DATAFLOW.md:117). `recordLog` NOT reusable (no source/precision/ts params, forces estimated on sleep, no recovery branch) → ingester calls `appendEvent` directly. `newEventId` (events.ts:10-14) non-deterministic, sort-order invariant load-bearing for the fold (schedule.ts:37-39) → identity must be payload-level. `appendEvent` propagates PK violations, no upsert. `migrate()` CREATE-only, append DDL fine; `profile` table exists but unused — new `wearable_tokens` table anyway (own shape: expiry, provider PK). Key-gating idiom three-part (rails.ts:104-106, order/route.ts:24, cart/route.ts:88). Route pattern: try-json → parse gate 422 → getDb+migrate → lib call (log/route.ts:11-27). No auth primitives anywhere — webhook signature verify is the repo's first. Fetch idioms: SSRF guard + timeout + final-host recheck (extract.ts), bearer + text()-first error (rails.ts:136-160); no retry/backoff exists yet. Schedule fold marks sleep slots done by SleptLogged date-join (schedule.ts:72-73,92-95); SessionLogged joins by slot_id only → whoop workouts can't auto-mark (correct). `localDate` mandatory for all day-joins (dates.ts:16-18; two prior UTC-rollover bugs). Tests: in-memory libSQL per test, mocked-fetch idiom in rails.test.ts:125-224, integration gating skipIf. Webhook + OAuth callback need a public URL → live webhook verify deferred to prod deploy; sync path covers local. Whoop v2: auth-code OAuth, rotating refresh, webhooks notification-only (IDs → follow-up GET), 100/min. `HOUSEHOLD_ID = "hh-jake"` hardcoded in all routes (P4 debt, unchanged here).

**Creativity beat.** Alternatives: (1) aggregator (Junction) for both providers — rejected: $300/mo floor vs free, unverified ToS, BYOO for Whoop anyway; (2) poll-only (cron-less sync button, no webhooks) — rejected as the *whole* answer since staleness kills the "tonight's dinner reflects today's recovery" promise, but sync ships alongside webhooks as backfill + dev path. 10x-vs-asked: the full P6 recovery-tuned living draft + repair engine — needs a planner and real data; the advisory flag is its deterministic seed. Simplest form that works: OAuth + CAS token store + one mapper path shared by webhook and sync + latest-wins reads; no queue, no encryption ceremony, no Garmin abstraction (a second provider later adds a table row and a mapper, not a framework).

**Decomposition.**
1. Token store + Whoop client: `wearable_tokens` DDL, `lib/whoop.ts` (authorize URL builder, code exchange, CAS refresh + in-process chain, authed GET with one 401-refresh-retry, key-gate throw); mocked tests incl. the concurrent-refresh race (criteria 1's lib half, 2, 3).
2. Mappers + idempotent ingest: record→event mappers with quality/date rules, `ingestWhoopRecords` (latest-per-external_id read, skip/append), contract additive fields + schema_version 2; regression tests (criteria 4, 5).
3. Routes: connect, callback (state gate), webhook (signature verify + in-request follow-up GET), sync; key-gated 503s; connect link + badge on / (criteria 1, 6, 7).
4. Recovery view + schedule join: `lib/recovery.ts`, /api/schedule day decoration, advice threshold (criterion 8).
5. Live probe + eval + docs: RUN_INTEGRATION suite from captured shapes, README (env vars, dev-app registration steps, webhook URL config), docs delta — WORKPLAN:67 re-sequencing wording, DATAFLOW invariant 3 sharpened (plan vs slot-status), PRODUCT § wearables v0 note — spec close-out (criterion 9 + docs).

**Test strategy.** Unit (mocked fetch): exchange/refresh/CAS-race/401-retry/signature/mappers/idempotency. Pure: recovery view, advice flag, quality thresholds, localDate joins incl. midnight-spanning sleep. Regression: pantry rebuild + schedule fold with whoop events interleaved. Integration (gated): live token'd GETs assert real shapes. Live-verify: blocked on Jake registering the Whoop dev app + connecting his account (surface: needs WHOOP_CLIENT_ID/WHOOP_CLIENT_SECRET in env, redirect URI registered); until then sync-path verification runs against recorded fixtures — same precedent as the Instacart key gate.
