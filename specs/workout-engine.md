# Spec: workout-engine (P5 data layer pulled forward — structured workouts, exercise history, progression, goals, week proposal)

Jake's build-the-backend loop directive (2026-07-26): workout history/schedule/completion, exercise history used to build workouts, goals and progress used to build schedules. Same re-sequencing move as the spine and wearables: the deterministic data layer ships now, headless; the P5 intelligence (repair engine, video extraction, autonomy ladder) stays in its phase.

**Intent.** Workouts become first-class data, not just titled slots. A structured workout lives in the library (`kind: "workout"`: exercises with target sets×reps and optional weight); doing it writes per-set `SetLogged` events (mid-session durability — the docs' P5 pre-commitment, DATAFLOW:43) plus the existing `SessionLogged` as the finisher that marks the slot done. Exercise history becomes a pure reader (every set you've ever logged, per exercise, household-local dates), and history starts building workouts: a deterministic double-progression rule turns your last performance into next targets ("hit 3×8 @ 135 → load 140"), served as response data when you fetch a workout — advice, never a write (the recovery-`advice` precedent, not the suggestion pair — that pairs with a real UI surface later). Goals get their event (`GoalSet`, latest-wins per goal_id) and a progress reader (strength: best set vs target; cadence: sessions per week), and goals start building the schedule: a deterministic proposer composes next week's workout slots (cadence goal → N days spread across the week, templates rotated least-recently-done first) returned as a proposal the user applies through the existing schedule POST — suggest-only holds, the proposer never writes the plan (DATAFLOW invariant 3).

**Acceptance criteria.**
1. **WorkoutPlan in the library.** `StructuredPlan` becomes a discriminated union on `kind`: the existing recipe shape unchanged, plus `WorkoutPlan {plan_version: 1, kind: "workout", title, exercises: Array<{name, sets, reps, weight?, unit?, note?}>}` (≥1 exercise; name/sets/reps required, sets/reps positive integers, weight positive number needing unit). POST /api/workouts with an untrusted body → parse gate (422 with reason on bad shapes) → library row `kind: "workout"`; GET /api/workouts lists them (id, title, exercise count). Saving writes a `WorkoutSaved` event (the RecipeSaved pattern).
2. **No cross-kind leaks.** `listRecipes` returns only `kind: "recipe"` rows (Cookbook, /api/recipes, week picker unchanged in behavior); new `listWorkouts` returns only workout rows. The guard lives at the LIB layer, not just pages (reviewer finding 1): `recordCooked` rejects a non-recipe library_id with a "not a recipe" error the /api/cook route maps to its existing 404-shape (never an uncaught 500), the cook page renders the same honest message, and the cart builder skips non-recipe ids in both the `library_ids` body path and (defensively) the plan path. Existing library tests keep passing with the filter in place (fixtures already set kind).
3. **Set logging.** New event `SetLogged {session_id, exercise, set_index, reps, weight?, unit?, rpe?, slot_id?, library_id?}` via POST /api/log `{kind: "set", ...}` (parse gate: exercise/session_id/reps required, reps/set_index positive ints, rpe 1-10, weight needs unit); precision `"exact"` (the lifting dial, UX.md:63). `SessionLogged` gains additive `session_id?` and `library_id?` (same schema_version-2 convention as `external_id`; parseLog session branch accepts them). All existing folds ignore `SetLogged` (pantry rebuild + schedule regression-tested); the schedule join is untouched — the finishing `SessionLogged {slot_id}` still marks the slot done.
4. **Exercise history.** `exerciseHistory(events)` pure reader: per normalized exercise name, chronological sessions `[{date (household-local via localDate), session_id, sets: [{set_index, reps, weight?, unit?, rpe?}]}]`, fold-ordered (byFoldOrder), sets grouped by session_id, deduped nothing (append-only truth). Served at GET /api/exercises (names + last-done + best set) and GET /api/exercises/[name] (full history).
5. **Progression = history → next targets.** `nextTargets(plan, history)` deterministic rule, documented at the definition: for each exercise in a workout plan, look at its most recent session; W = the MAX weight among that session's weighted sets (warm-ups at lower weights ignored; weightless sets ignored — reviewer finding 2); all sets AT W reached target reps → next target = W + 5 (lb) / + 2.5 (kg) (flat increment v0, no exercise taxonomy); any set at W short → repeat W; no session with a weighted set for that exercise → no target (cold-start honesty, no invented numbers). GET /api/workouts/[id] returns the plan with per-exercise `next: {weight, unit, reason}` response data — no event written, no SuggestionMade (non-goal: pairs with the workout UI).
6. **Goals.** `GoalSet {goal_id, title, kind: "strength" | "cadence" | "custom", exercise?, target_weight?, unit?, target_reps?, per_week?, cleared?}` — latest event per goal_id wins, `cleared: true` removes (the PreferenceSet idiom, no view table — pure reader at this scale). POST /api/goals (parse gate: title+kind required; strength needs exercise+target_weight+unit; cadence needs per_week ≥1) with goal_id minted server-side when absent; GET /api/goals returns active goals each with `progress`: strength → `{best: {weight, unit, reps}, target_weight, pct}` from exercise history (best set at reps ≥ target_reps, default 1; unit-converted via lib/units where dimensions match, honest null when nothing converts); cadence → `{this_week, per_week, weeks: last 4 Monday-start weekly session counts}` where the count resolves latest-per-external_id first (a revised whoop workout counts ONCE — reviewer finding 4; events without external_id count individually), structured+loose both count, SetLogged never counts (sessions only).
7. **Goals build the schedule.** `proposeWorkoutWeek(goals, workouts, events, mondayISO)` deterministic composer for the NEXT Monday-start week: cadence goal `per_week: N` (no cadence goal → no proposal, cold-start honest) → N workout slots spread deterministically (day order Mon, Wed, Fri, Sat, Tue, Thu, Sun), templates assigned least-recently-done first — "last done" per template = the latest SessionLogged carrying that `library_id` in fold order (reviewer finding 3); never-done templates come first, in listWorkouts order, then least-recent ascending — each slot `{lane: "workout", title: plan title, library_id}`. GET /api/schedule/propose returns `{days: [...]}` as PROPOSAL data; applying is the client POSTing /api/schedule (the only plan writer — invariant 3 intact). No library workouts → empty proposal with honest reason.
8. **Nothing breaks.** Pantry rebuild invariant green with SetLogged/GoalSet/WorkoutSaved interleaved; schedule fold, cart-from-plan, replenisher, whoop ingest all as shipped. tsc clean.
9. **Docs delta.** DATAFLOW SetLogged row planned→shipped + goals/progression readers noted; WORKPLAN P5 note (data layer pulled forward, intelligence stays); contracts comment updates (StructuredPlan union arrival, slot library_id lane-agnostic wording).

**Non-goals.** Workout video/URL extraction and any extraction-adapter change (parseExtraction stays recipe-only; WorkoutPlan enters via API, extraction subtype is P5). Any UI (headless APIs; grid/Today/workout screens are the design pass). Repair engine, deload/block periodization, program-engine repositioning (ahead/behind) — E proper stays P5; the proposer is a week skeleton, not a program. Suggestion-pair logging for progression/proposals (needs a real accept/dismiss surface; the contracts exist when it comes). Recovery/strain-aware progression (P6 tuning). Editing/deleting workouts (create + list v0; a re-POST makes a new row). Exercise taxonomy/aliases beyond lowercase-trim normalization. Auth (HOUSEHOLD_ID constant as everywhere).

**Creativity beat.** Alternatives: (1) sets inside SessionLogged payload (one event per session) — rejected: loses mid-session durability, contradicts the docs' SetLogged pre-commitment, and makes per-set history a payload dig; (2) full program engine now (blocks, deloads, ahead/behind) — rejected: composition without real training history is guessing; UX.md:43 says beyond next week is skeleton-only anyway. 10x-vs-asked: the P5/P6 living draft with repair + recovery-tuned loads — bolts onto exactly these events later ("later phases add readers, not rewrites", WORKPLAN:20). Simplest form that works: one new library kind, one new event type + one extended, three pure readers (history, progression, proposal), goals as latest-wins events — no new tables, no LLM, no writes from inference anywhere.
