# Spec: workout-video-extraction (backend-complete workstream 6, final)

Branch `feat/workout-extraction` off `feat/coach-reflect` (PRs #20-25 open; stacked — PR base = `feat/coach-reflect`).

## Intent

The second vertical lights up on the same engine (PRODUCT.md:105): share a workout video or page the same way you share a recipe, and it comes back as a structured workout template — exercises, sets, reps, the source video attached as a form reference — ready for review and save into the library the program engine already draws from. One intake gesture, the model tells the kinds apart (UX.md:83 "same gesture"); the extraction route stops being recipe-only and `parseExtraction` stops hard-rejecting workout shapes.

## Acceptance criteria

1. The extraction RUBRIC becomes a two-kind intake: shape 1 recipe (unchanged fields + required `"kind":"recipe"`), shape 2 workout (`{"kind":"workout", "title", "exercises":[{"name","sets","reps","weight"?,"unit"?,"note"?}]}` — no confidence block (nothing stores it; dead weight cut), rep RANGES resolve to the lower bound with the range noted in `note`), shape 3 error (unchanged). Byte-identical across calls after the change (one-time cache invalidation, then stable).
2. `parseExtraction` dispatches on `obj.kind`: absent or `"recipe"` → today's recipe path byte-for-byte; `"workout"` → the branch builds `{title, exercises, source_url, source_embed?}` and hands the WHOLE thing to `parseWorkoutPlan` — the ONE shape authority for both the model path and the /api/workouts body path; it alone gates source fields and computes plan_version (no duplicated logic in extract.ts). `ExtractionResult.plan` widens to `StructuredPlan`.
3. `WorkoutPlan` gains optional `source_url` + `source_embed` (contracts): `plan_version` becomes `1 | 2`, emitted 2 only when `source_embed` is present (the recipe idiom, contracts.ts:391) — computed inside `parseWorkoutPlan`, nowhere else. `parseWorkoutPlan` gates both (source_url must be http(s) when present; embed strict — malformed is an error, not a drop). `parseSourceEmbed` MOVES to lib/contracts.ts (the SLOT_LANES one-authority precedent) — exporting it in place would make extract.ts and workouts.ts import each other.
4. `POST /api/workouts` with an extracted plan persists source fields; `saveWorkout` passes `plan.source_url ?? null` so re-sharing the same video UPDATES the existing template instead of stacking duplicates (the recipe dedup branch, library.ts:26 — keyed on household+kind+source_url, so a recipe and workout from one URL never collide).
5. `POST /api/recipes` refuses a workout-shaped body: `parseExtraction` returning `kind:"workout"` → 422 "that's a workout — save it via /api/workouts" (never silently stored as a recipe).
6. `POST /api/recipes/extract` returns whichever kind the content is (`{ok:true, plan}` with `plan.kind` discriminating) and front-gates through `readJsonObject` (today it raw-destructures — inconsistency fixed while touched). Photo intake stays recipe-only BY GUARD, not by assertion: `extractRecipeFromImage` maps a `kind:"workout"` result to `{ok:false, reason:"photo intake is recipe-only for now"}` (the shared rubric means the model CAN return one).
7. A TikTok/YouTube workout video flows end to end: adapter caption → model → `kind:"workout"` plan with `source_embed {provider, video_id}` → save → library row with populated `source_url`, `WorkoutSaved` event, template visible to `proposeWorkoutWeek`/`nextTargets`.
8. Tests: extract-parse unit tests for the workout branch (valid, kind dispatch, garbled exercises → strict reason, recipe path unchanged); a captured workout-video fixture + integration eval case (`mustGround` exercise names, live-gated); journey demands for the save flow + the /api/recipes kind guard + hostile paths. Live probe: one real model call on the workout fixture returns a grounded `kind:"workout"` plan.

## Non-goals

Per-exercise video refs ("at the exercise it demonstrates", PRODUCT.md:22 — needs multi-clip data; plan-level embed is the v1, same as recipes). Photo-of-workout-card intake (photo path stays recipe-only). Tempo/muscle-group/equipment fields (PRODUCT.md:22's fuller shape — needs catalog vocabulary; name/sets/reps/weight is the working skeleton the program engine consumes). Renaming `/api/recipes/extract` (cosmetic; UI work decides the final intake naming). Voiceover-only video transcription (thin-caption guard stands). Instagram (hard-blocked upstream).

## Creativity beat

Alternatives: (a) caller declares kind (`{url, kind}`) — rejected: the user shouldn't have to say what a link is; "same gesture" is the promise, and the model reliably knows a squat program from a curry; (b) separate workout rubric + second model call on recipe-failure — rejected: doubles cost and latency on the main intake path for zero accuracy gain. 10x version: full movement ontology (tempo, muscle groups, equipment, per-exercise clips) — needs vocabulary and UI that don't exist. Chosen: one two-kind rubric, dispatch in the existing gate, reuse the manual-entry validator as the one shape authority, plumb source fields through the existing save/dedup machinery. Simplest form that works: ~4 focused edits (rubric, dispatch, contracts+gate, save wiring) and the second vertical is live on every intake surface except photo.
